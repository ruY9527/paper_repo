    Backtracking Agent Applications Security Incidents

    ← 返回首页 · 最近发布的高价值论文

    信息标记约定：本文用 P 表示论文原文明确声称，用 L 表示相关文献已有结论，用 I 表示基于证据的合理推断，用 S 表示不确定的猜测。涉及图像融合的内容，原文没有任何实验或设计，相关段落会显式标注为 I 或 S，并与论文事实分开。

    1. 研究问题、重要性与价值¶

    问题定义【P】。 智能体应用（LLM-powered agent application）发生安全事件后，组织要回溯找出 CEP（compromise entry point，入侵入口点），据此修复损害并防止复发。CEP 的定义很具体：一次 API 调用，其返回值首次把恶意数据带进应用，并用三元组定位，即 API 名、源码文件名、调用点行号。

    可用的证据材料很不对称【P】。 分析者手里只有两类东西：一类是 trajectory log，记录规划、调用工具、回忆记忆等 agent functionality 的序列；另一类是应用源码。应用专属的函数调用日志往往很稀疏，原因很实际：开发者不会为尚未出现的新型攻击预置日志语句，完整日志又受开销和隐私约束被关掉。

    语义鸿沟是核心障碍【P】。 trajectory log 处在 agent functionality 抽象层，CEP 候选处在 app code execution 层。GPT-Researcher 的 MC-Poison 事件里，静态污点分析先抽出 1,895 个 API 调用作为污点源候选；用日志里的独特字符串（如 Starting research for ...）反查日志打印语句、定位调用者、剪掉不可达路径，降到 1,518 个。到这一步就断了：剩下 1,518 个候选里，哪些属于「知识库检索」这个功能，代码本身不写。判断 loader.load() 是否在读知识库，要回溯 loader 的定义、检查 loader_dict 里每个类的 load、结合调用者名 _load_document 推断开发者意图。逐个做需要数小时。

    为什么重要【P + L】。 GPT-Researcher 发布后累计 24,027 stars；论文引用 Gartner 预测，企业智能体应用占比从 2025 年不足 5% 升到 2026 年底约 40%。IPI（间接提示注入）和 MC-Poison（记忆与上下文投毒）是 OWASP 智能体 Top 10 中最普遍的类别，已有多个 CVE 和红队报告。L：后续工作也把提示注入当作独立事件类处理，例如 IEEE GAISS 2026 的取证分类与事件响应手册（Jain 2026），NeurIPS 2025 的 WASP 则为 web agent 抗注入建立了基准（Evtimov et al.）。需求侧已经成形，工具侧仍缺一环。

    价值【P】。 定位到 CEP 之后，两类干系人拿到可执行结果：修复管理员得到具体处置对象，比如从数百份文档的知识库里删掉某一份被投毒文件；开发者得到日志语句应插在哪个调用点之前的建议，使应用以后可诊断。论文报告分析者用 Origin 在全部 8 起事件中各自只得到 1 个 CEP 候选，检查范围相对完整污点图减少 64% 到 94%。

    2. 之前是否解决过，为什么不够¶

    轨迹日志类故障诊断【P】。 现有工作输出的是错误的 agent 执行状态、出错的 agent 或 agent owner。它们回答「哪个环节判断错了」，不给出源码级函数调用。

    检测与归因类工作【P】。 这类输出 faulty agent 或 LLM tool call。tool call 与源码函数不在同一层，拿到工具名仍无法定位 loader.load() 这样的调用点。

    预防式信息流控制【P】。 它在运行时拦截，输出仍是 LLM tool call 级别。【L】同一方向的后续研究包括 Progent 的可编程权限控制、面向 AI agent 的信息流控制（Costa et al. 2025）、Dual-LLM 模式在 Google ADK 中的工程化（Huang & Lee 2026）。这些工作的目标函数在攻击发生之前拦住它；攻击已经成功时，仍需要回溯。

    静态污点分析器【P】。 Joern、CodeQL、Pysa 能算变量级传播路径，但没有 agent functionality 抽象。论文把 ground truth 的源和汇直接喂给它们，让它们只负责验证路径，结果 Table 4 里 24 个格子中仅 1 个成功（MetaGPT IPI 上的 Pysa）：Joern 全败，CodeQL 全败。失败原因包括间接调用目标未解析、嵌套字典访问丢污点、库调用未建模、对象属性与文件数据库「先写后读」丢失依赖。Pysa 即使报出 4 个调用点，也只有 1 个在正确路径上，分析者还得从 14 个函数的路径里反推哪个是入口。

    传统根因分析与 APT 溯源【P】。 面向内存安全、数据竞争的根因分析针对的是有 bug 的代码；这里代码本身在条件判断和语句顺序上没问题，问题在于不可信外部信息源与应用边界之间缺少校验。APT 溯源依赖 OS 审计日志；智能体场景里没有这种日志，只有高层轨迹和源码。

    不足可以归纳成一句话：现有工具各自占据一端，从高层日志推不出调用点，从底层污点推不出功能语义，中间缺一层可查询的桥。

    3. 作者的思考路径重建¶

    以下只用论文之前的背景、失败模式和经验观察来推演，不把论文的贡献当前提。

    第一步，从日志剪枝的成功处接着往下想【I】。 分析师已经证明了一个有用动作：拿日志字符串回源码里找打印语句，找到调用者，剪掉不可达路径，候选从 1,895 降到 1,518。这个动作之所以有效，是因为日志文本是源码里的字面量，天然构成日志层到代码层的锚点。问题在于日志只覆盖被打印的部分，剩下的候选没有锚点。

    第二步，观察候选代码缺的是什么【I】。 Listing 2 里 ret_data、loader_dict、loader 这些名字都不带「知识库」语义。判断语义要靠跨语句证据：变量定义、类实现、调用者意图。既然单条语句不够，就需要把证据沿数据依赖串起来，变成图上的路径。

    第三步，从背景里挑一个可以枚举的语义轴【P + I】。 论文第 2 节把信息源分成外部（用户输入、网页、邮件、LLM 生成内容等）和内部（知识库、记忆）。功能很多，信息源类型很少。检索知识库和回忆记忆是两个功能，都碰内部源；接收用户指令和抓取网页都碰外部源。把「功能」压成「与哪类信息源交互、读还是写、是否在拼 prompt」这几个维度，词汇表就从开放集合缩到 5 个 region。这是编译器思路：两层之间加一层 IR，上层不必理解下层实现细节，下层不必理解上层语义。

    第四步，想清楚 region 到变量怎么落地【I】。 函数名、变量名、语法特征都不可靠：两个 load 可以分别读网页和读知识库；x.format(y) 可能拼 prompt，也可能拼错误信息。可靠的信号是开发者对少数直接调用信息源 API 的函数的标注。把标注沿污点路径传播：读源的函数向后传，写源的函数向前传；prompt 拼装标签只在函数内传。再用一张条件动作表把证据合成 region 决策。这样只要求开发者标 2.4% 到 8.9% 的函数。

    第五步，接受不完备并把它写进设计【I】。 静态分析完不成的事（C2 智能体、框架间接分发）明确划到范围外，保留 UNK region 兜底。领域已知的 five regions 可由分析者替换，只要提供对应的信息源映射表。这种取舍在 5 个应用、8 起事件上被验证够用。

    4. 方法的 Intuition¶

    一句话：把「智能体在做什么」压缩成少量带语义的 region，把「数据怎么流」保留为变量级污点图，再用跨平面边把两者钉在一起。

    分析者不再逐条看 1,518 个候选，而是问一个区域级问题，例如「有没有数据从规划与执行区流进 prompt 厨房区，又从 prompt 厨房区流回规划与执行区」。图回答这个问题，返回一个很小的子图。分析者在这个子图上挑出源变量和汇变量，再问一个变量级问题，拿到从入口到攻击效果的函数级路径。两次查询替代数小时代码阅读。

    Region 直觉来自信息源类型：外部只读是感知 Per，外部写或读写是规划执行 PA，内部读写是回忆反思 RR，主要拼 prompt 的是 PK，剩下 UNK。

    5. 具体方法：输入、处理、输出¶

    以 GPT-Researcher 的 MC-Poison（KB）事件为主线走一遍完整 pipeline。

    输入【P】。 两样东西：应用源码；开发者提供的一张「函数到信息源」映射表，标注函数接触外部源 EXT 还是内部源 INT。表中 SWE-agent 只标了 17/713 个函数（2.4%），Quivr 标了 22/246（8.9%）。为了减少人工，Origin 用 LLM 读函数的 API 调用、相关代码和识别规则，产出结构化报告：每个调用的决定、解释、支撑代码位置、缺失信息。人从「标注」变成「审核报告」。 knowledge collection 速度提升 15.4% 到 75.0%，准确率提升 8.3 到 50.4 个百分点。

    步骤一，构建变量平面【P】。 从源码里每个 API 调用的返回值出发，做上下文敏感、流敏感、字段敏感的前向污点传播。因为起点是所有 API 调用，任何符合 CEP 定义的调用必然落在某条传播路径上。同一变量出现在不同语句里算不同节点。实现基于 Joern 4.0.360，并用 Pyrefly 0.45.0 补类型推断：把 yield / yield from 改写成 return 以支持生成器表达式；用 CFG 可达性显式传播 self.x 这类实例变量；用打补丁的 Pyrefly 做类型感知的间接调用解析，再叠加上下文敏感的类型链跟踪和值集分析。

    步骤二，构建函数平面与跨平面边【P】。 只要某个函数里有变量进入变量平面，该函数就进入函数平面；跨平面边把函数连到它定义或使用的每个变量。

    步骤三，区域推断【P】。 两类规则。标签传播规则 3 条：读信息源的 API 调用沿污点路径向前传标签；写信息源的向后传；prompt 拼装标签只在函数内传。条件动作规则 9 条，按四个问题决策：是否接触信息源、读还是写、主导信息源类型、是否主要拼 prompt。压缩后是：不接触源得 UNK；外部读得 Per；外部写或读写得 PA；内部读、写、读写得 RR；读写且拼 prompt 得 PK。 rule 9 是后来补的，因为发现 prompt 拼装可以在读完任意信息源之后就开始，不必紧挨 LLM 上下文窗口。

    步骤四，CLDG【P】。 形式化为六元组 G = (R, V_fn, λ, E_cross, V_var, E_var)。R 是区域到功能的映射，λ 给每个函数节点赋区域，E_cross 连函数与变量，E_var 是变量间污点边。跨函数的污点边自然映射为函数级路径上的一条边。

    步骤五，查询【P】。 分析者先提交区域级查询。例如 GPT-Researcher MC-Poison（KB）用 CHECK (PK DEPENDS_ON RR) AND (PA DEPENDS_ON PK)。求值时先用 λ 和 E_cross 找到源区与汇区的变量集合，在变量平面做前向与反向可达性，交集就是位于某条源到汇污点路径上的变量；再把这个交集投影回函数平面得到结果图。分析者在结果图里挑源和汇，提交变量级查询，例如 CHECK node.5110 DEPENDS_ON node.4216。Origin 用调用图和控制流图枚举控制流可行的污点路径，输出 CEP 与函数级路径。链式算子 → 支持把后一个查询限定在前一个查询返回的子图上。

    输出【P】。 三元组 CEP（API 名、文件、行号）加一组从 CEP 返回值变量到攻击效果变量的污点路径。_load_document 里的 loader.load()（Listing 2 第 83 行）在 GPT-Researcher 案例中被识别为知识库加载入口；该事件返回 4 条函数级路径，19 个函数，最终 1 个候选，用 2 次查询。

    关于图像融合侧重点的诚实说明【I】。 这篇论文没有研究图像融合，也没有动态算子调度、退化感知路由、自适应提示生成、多模态工具链、端到端质量闭环或融合质量指标。任何把这些说成论文内容的写法都是错的。可以做的只是明确标注的迁移假设：CLDG 的 PA 区在结构上类似「调度决策发生的地方」，PK 区类似「自适应提示生成」，RR 区类似「退化历史或先验的回忆」，Per 区类似「传感器或退化输入」；函数级路径可以充当路由决策的审计链【I】。论文明确承认的框架间接调用解析失败，在多模态工具链（图像编码器、外部视觉 API、插件式算子分发）里会放大，因为那里大量调用经过框架分发【I，S】。多阶段 MC-Poison 的「投毒阶段 → 利用阶段」两条路径构成一种闭环，但闭环服务于攻击链，不服务于融合质量提升【I】。论文的质量代理指标是候选缩减率、区域推断 precision/recall 和查询耗时，与 PSNR、SSIM 无任何对应关系【I】。

    6. 核心数学推导¶

    这篇工作没有优化目标或新定理，贡献是定义与操作流程。数学负担主要在集合与图可达性，下面从零走一遍。

    基础概念。 把程序看成一张有向图 E_var：节点是变量（按语句位置区分），边 u → v 表示 u 的值流到 v。「可达」就是从某节点沿有向边能走到哪里。前向可达 Reach_F(S) 是从源集合 S 出发能到达的所有节点；反向可达 Reach_B(T) 是倒着走能到达 T 的所有节点。

    构造函数平面的规则【P】。 V_fn = { f | f 中存在变量 v ∈ V_var }，即函数里只要有变量进了污点图，这个函数就入图。E_cross 把 f 连到它定义或使用的每个 v。λ 是函数到 {Per, PA, RR, PK, UNK} 的标注函数。

    区域级查询的推导【P】。 设查询为 R_src DEPENDS_ON R_sink。

    第一步，把区域翻译成变量集合：

    \[ `V_src = { v | ∃f ∈ V_fn, λ(f)=R_src 且 (f,v) ∈ E_cross }` \]
    \[ `V_sink = { v | ∃f ∈ V_fn, λ(f)=R_sink 且 (f,v) ∈ E_cross }` \]

    第二步，找出所有既在源区下游、又在汇区上游的变量：

    \[ `I = Reach_F(V_src) ∩ Reach_B(V_sink)` \]

    为什么要取交集：只在 Reach_F 里的变量可能流向别处，与汇区无关；只在 Reach_B 里的变量可能来自别处，与源区无关。同时满足两者才可能位于某条源到汇的路径上。这就是论文查询求值的核心一步。

    第三步，把变量交集投影回函数平面。若存在污点边 (u,v) ∈ E_var，且 u、v 都在 I 中，u 属于函数 f1、v 属于函数 f2，就在结果图里加边 (f1,f2)。

    逻辑连接词按集合运算解释：AND 对节点集和边集取交，OR 取并。链式 Q1 → Q2 表示先算 Q1，再在 Q1 返回的子图上算 Q2。

    变量级查询的推导【P】。 给定节点 id 作为源和汇，直接切图会包含实际执行中不可行的路径。Origin 加入调用图和 CFG 约束，只枚举控制流可行的污点路径。每条路径上的变量按「所在函数」做映射，就得到函数级路径序列，这正是分析者读懂攻击链需要的粒度。

    区域推断的形式化【P】。 标签传播是沿污点边的不动点式传播：读源标签前向走、写源标签后向走、prompt 拼装标签函数内走。条件动作规则是一张决策表，把四元证据 (IS, R/W, MainIS, Asm) 映射到区域。举一个具体推导：get_chat_history 里 execute() 前有 .from_("chat_history").select("*")，开发者标 INT 并说明 chat_history 是 agent memory；读标签前向传入该函数；无 prompt 拼装标签；四元证据是 (Yes, R, Int, No)，命中 rule 5，归 RR。

    精度指标【P】。 Table 6 用的是常规定义：precision = TP/(TP+FP)，recall = TP/(TP+FN)。SWE-agent 为 140 TP、20 FP、20 FN，两个值都是 0.875；aider 为 229 TP、100 FP、95 FN，precision 0.696、recall 0.707。

    7. 实验设计：问题 → 实验 → 答案¶

    实验对象：5 个开源智能体（GPT-Researcher 24,027 stars / MAA、Quivr 38,575 / SAA、aider 38,237 / SAA、MetaGPT 59,192 / MAA、SWE-agent 17,716 / MAA），8 起事件，覆盖 IPI、MC-Poison（记忆 M 与知识库 KB）、以及 IPI + MC-Poison 复合攻击。

    RQ1：能否正确找出 CEP 和路径？ 实验：把 ground truth CEP 与匹配真实执行的污点路径作为成功标准，让分析者用 Origin 做回溯；同时把 ground truth 源和汇直接喂给 Joern、CodeQL、Pysa 做对照。答案【P】：8/8 成功，每起事件 1 个候选；5 起用 2 次查询，3 起用 4 次。对照组 Joern 与 CodeQL 全败，Pysa 只在 MetaGPT IPI 上成功一次。两阶段攻击（Quivr MC-Poison M）需要每个阶段各做一轮区域级和变量级查询，两条函数级路径里共享 chat_history 表这一参数，据此判定 CEP 是接收聊天消息的用户接口。

    RQ2：区域推断准不准？ 实验：对每个进入函数平面的函数，用人工标注的 region 作为 ground truth，比 TP/FP/FN。答案【P】：precision 与 recall 落在 0.70 到 0.88；MetaGPT 最高（0.8497 / 0.8798），aider 最低（0.6960 / 0.7068）。aider 低的原因是它的能力以交互式命令暴露，各命令的污点路径短且互不连通，一条路径上的标签传不到另一条命令的函数。

    RQ3：检查范围缩小多少？ 实验：比较区域级查询结果中的变量节点数 |Vq| 与完整变量平面 |Vvar|。答案【P】：比值在 6.49% 到 35.76%。PK 是关键杠杆，11 条区域级查询里 9 条包含 PK；PK 函数很少（Quivr 1 个、aider 2 个、SWE-agent 3 个），查询涉及 PK 时结果被限制在与这几个函数传递相连的节点上。同一条 IPI 查询在 SWE-agent 上是 9.56%，在 GPT-Researcher 上是 35.76%，差别主要来自 PA 区大小（64/160 对 133/244）。

    RQ4：时间和内存？ 实验：在 Intel Core Ultra 9 285、128 GB RAM、Ubuntu 24.04 上分阶段计时。答案【P】：CLDG 构建占单应用总时间 95% 以上（aider 109.09 s 最高），区域推断 0.03 到 1.97 s，单次查询平均 5.63 到 89.38 ms，峰值内存最高 7.00 GB。构建与推断是一次性离线成本，逐事件成本只有查询。

    RQ5：需要多少开发者知识？ 实验：统计 EXT/INT 标注数占应用函数数比例。答案【P】：2.4% 到 8.9%，最高 Quivr 22/246，最低 SWE-agent 17/713。

    RQ6：LLM 报告有用吗？ 实验：4 名不同背景参与者，每人做两次 10 分钟测试，一次手工标注，一次审核 LLM 报告，用两套不重叠的 200 函数集合并做顺序平衡。答案【P】：4 人速度和准确率都提升，速度 +15.4% 到 +75.0%，准确率 +8.3 到 +50.4 个百分点，最终 88.9% 到 100%。

    补充观察【P】。 智能体循环不会破坏回溯，只要 CEP 与攻击效果对应的调用落在循环之外；SWE-agent 的循环处在路径中间，静态污点仍能穿过。读写工具是通用函数时（aider 的 read_text/write_text、MetaGPT 的 aread/awrite），源到汇直接查询会返回大量无关路径，有效做法是从区域级结果里挑一个中间函数，把其中变量设为 waypoint。MetaGPT 的 CEP 来自上游 architect agent 写盘的规格文件被篡改，下游 engineer agent 正常读取，这属于通过应用既有协作机制跨 agent 边界发生的 IPI。

    8. Take aways¶

    1. 智能体安全事件的瓶颈不在「找不到污点路径」，而在「路径太多且没有功能语义」。GPT-Researcher 从 1,895 剪到 1,518 之后，剩下的工作全靠人读代码。
    2. 信息源类型（EXT/INT）、读写方向、是否拼 prompt 这三个维度足以把大量功能压成 5 个 region，这是全文最关键的建模决策【P，有效性限于 C1 范围】。
    3. 两层之间加一层可查询 IR，比让任一层单独承担全部语义更实际。CLDG 的双平面加跨平面边就是这个 IR。
    4. 区域级查询的价值可以量化：把变量平面压到 6.49% 到 35.76%，PK 因为函数数量少成为最强剪枝杠杆。
    5. 开发者负担可以压到 2.4% 到 8.9% 的函数标注，LLM 生成的审核报告进一步提升速度与准确率。
    6. 静态分析的边界是真实的：框架诱导的间接调用、动态分发的工具调用、LLM 运行时决策的 C2 智能体都在范围外。论文把这些写进 Discussion，没有掩饰。
    7. 现有污点工具即便拿到 ground truth 源汇也大多验证失败，说明「有静态分析器」与「能诊断智能体事件」是两件事。

    9. 最脆弱的假设¶

    首要假设【P + I】：agent functionality 的语义可以由「与哪类信息源交互、读还是写、是否主要拼 prompt」这组维度恢复，而且每个函数只落在一个 region。 整个 region-to-variable 映射、9 条条件动作规则和查询剪枝能力都压在这上面。脆弱点有三处。第一，五个区域是分析者自定的，换一套区域就要重做映射表和规则【P】。第二，通用工具函数天然跨功能，aider 的 precision 0.696、recall 0.707 已经暴露了这条假设的裂缝，论文用 waypoint 绕过，waypoint 本身依赖轨迹日志里有语义命名的中间步骤，这个前提并不总成立【I】。第三，一个函数同时读外部源、写内部源、又拼 prompt 时，MainIS 与 Asm 的判定需要人为裁决，rule 8 和 rule 9 是事后补出来的，说明规则集并非完备。

    范围假设【P】。 工作明确限定 C1（源码决定控制流），把 C2（LLM 运行时决定下一个功能）排除。OpenClaw、Hermes 这类 agentic loop 应用里，静态分析无法判断哪个工具调用真正引入了恶意数据。

    分析完整性假设【P】。 静态污点分析被假定足以覆盖 CEP 所在路径，但 LangChain 等框架的工具分发会让间接调用目标解析失败，对应路径直接缺失。

    攻击模型假设【I】。 CEP 被定义为「返回值带恶意数据的 API 调用」。若恶意数据以图像像素、音频波形、模型权重或工具 schema 形式进入，且没有可追踪的返回值，这个定义覆盖不到。

    11. 反例设计¶

    1. 抹掉语义锚点【I】。 构造一个应用，所有文件 I/O 都走通用的 read_text/write_text，轨迹日志只记录「命令执行完成」这类无语义字符串，不记录命名步骤。区域级查询会返回几乎整个变量平面，waypoint 无从选起。aider 和 MetaGPT 已经半个脚踩在这里，论文靠 waypoint 解围；把 waypoint 的前提去掉，方法就退化成手工看 1,518 个候选。
    2. 多模态入口【I】。 让恶意内容藏在图像像素里，经视觉编码器变成向量写进向量库，另一轮对话中检索出来影响生成。若污点分析不建模编码器与向量库调用，CEP 整条路径都不在 CLDG 里。这正好落在论文承认的库调用未建模与框架分发失败两类缺口上。
    3. C2 运行时决策【P + I】。 智能体每轮由 LLM 选下一个工具，恶意数据由其中一个工具引入。源码层面所有工具对称，静态分析无法判定实际执行走了哪条，论文自己把这个场景划到范围外。
    4. 标签污染【I】。 把 get_chat_history 的 INT 标成 EXT，标签传播会把 RR 区域的一大片函数染成 Per，区域级查询 RR DEPENDS_ON PA 直接漏掉真正 CEP。0.70 级别的 baseline precision 说明系统对这类错误并不鲁棒。
    5. 主导信息源平局【I】。 设计函数同时读外部请求、写内部记忆、并拼 prompt，让 rule 8 与 rule 5/6 都可命中。规则表没有冲突消解机制，不同裁决给出不同区域，同一份日志会得到不同查询结果。

    13. Follow-up idea：带有来源令牌的智能体 I/O 中间表示¶

    动机【I】。 Origin 在事后从源码和标注里推断语义，代价是规则不完备、标签依赖人、框架分发与多模态路径丢失，C2 完全出界。把推断问题往前挪到编写阶段，可以从根上消掉这几处脆弱性。

    核心想法【S】。 设计一种 capability-typed 的 I/O shim，在应用与框架边界处自动生成 provenance token：任何从外部源或内部源进入的数据，都被打上来源、读写方向、时间戳、所在能力域的令牌；令牌随数据穿过 LLM 上下文序列化、工具调用、记忆写入、向量嵌入和多模态张量。运行时轨迹日志因此天然携带来源信息，事后回溯变成「带令牌的轨迹日志」与「轻量调用图」的一次连接查询，不再需要开发者标注信息源、不再需要 region 推断规则，也不依赖静态分析解析框架间接调用。对 LLM 运行时选工具的 C2 智能体同样成立，因为令牌跟数据走，不跟控制流走。

    与图像融合的连接【S】。 同一个 IR 可以同时承载退化标签和算子来源：图像进入融合流水线时带上传感器类型、退化类型、预处理算子链；每个融合算子消费和产生的张量都继承并追加令牌。这样既能做「这次融合决策依据了哪个退化估计和哪次历史回忆」的审计，也能在发生投毒时定位首个把不可信像素带进流水线的调用。动态算子调度的决策链、退化感知路由的依据、自适应提示的生成来源，都变成可查询的 provenance 图，而不需要另建一套融合质量解释方法。

    评估设计【S】。 在两个带视觉工具的智能体上做插桩，一个是图像融合流水线，一个是文档检索 agent；注入 IPI 与多模态投毒各若干起；指标用 CEP 唯一候选率、所需查询数、令牌在工具边界后的存活率、额外运行时开销。对照组是原始 Origin 风格的区域推断。证伪条件要提前写清楚：如果令牌无法在不改写框架内部代码的前提下穿过 LLM 上下文序列化，或者存活率低于 90%，这个想法就退化成需要重写整个生态的方案，价值大幅下降。

    为什么这是新方向而非增量【I】。 现有工作是事后分析（本文）、事前防御（信息流控制、Dual-LLM）或攻击基准（AgentDojo、WASP）。把 provenance 作为应用与框架之间的显式编译期与运行期契约，让分析和防御共享同一份语义载体，改变的是「语义从哪里来」这个问题的答案，而不是在同一套规则表上加减条目。
